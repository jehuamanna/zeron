# Paid courses spike results (Phase 11, slice 1)

Date: 2026-10-16 · Platform: Linux x86_64 (Intel Core Ultra 9 275HX) · Rust 1.99 · Code: `spikes/paid-courses/` (throwaway, excluded from the workspace) · Decision record: [ADR 0017](../decisions/0017-paid-courses-and-licenses.md)

## Questions

1. Does chunked decryption behind the media gateway keep seeking and lesson start fast, and which chunk size should the format use?
2. Does the issuer-as-relying-party sign-in work with a loopback redirect through a real browser, and does it refuse the obvious attacks?
3. Which HPKE crate should wrap content keys to learner keys?

## 1. Chunked decryption through the gateway

**Setup.**

- `src/lib.rs` implements `zeron.chunked-xchacha20poly1305.v1` as ADR 0017 describes it:
  - an HKDF-SHA256 per-resource key;
  - XChaCha20-Poly1305 per chunk, with nonce = chunk index;
  - associated data binding the resource ID, the index, and a final-chunk flag.
- `DecryptingReader` wraps any `AsyncRead + AsyncSeek` and plugs into the **real** `media-gateway` crate as a `MediaSource`, exactly where the torrent stream plugs in today.
- The test video is 3 minutes of 1080p H.264 at about 8 Mbit/s with a keyframe every 2 s (182 MB, generated by ffmpeg).
- Reproduce:
  - `cargo test`;
  - `cargo run --release --bin chunked -- bench`;
  - `cargo run --release --bin chunked -- serve`, then open the printed page and press Run.

**Reader-level results** (warm page cache, one core). "Seek" opens a fresh reader, seeks to a random offset, and reads 512 KiB, as one gateway response does.

| Format | Sequential read | First byte p50 / p99 | 512 KiB p50 / p99 | Size overhead |
|---|---|---|---|---|
| Plaintext | 6.1 GB/s | 16 µs / 19 µs | 95 µs / 260 µs | — |
| 16 KiB chunks | 650 MB/s | 30 µs / 56 µs | 0.8 ms / 3 ms | 0.098% |
| **64 KiB chunks** | **1.2 GB/s** | **56 µs / 169 µs** | **0.5 ms / 1.0 ms** | **0.024%** |
| 256 KiB chunks | 1.25 GB/s | 284 µs / 506 µs | 0.9 ms / 2 ms | 0.006% |
| 1 MiB chunks | 1.4 GB/s | 682 µs / 940 µs | 2 ms / 2 ms | 0.002% |

Encryption at packaging runs at 0.8–1.3 GB/s, so a 2 GB course adds about 2 s to publishing.

**Through the gateway, with real decoders.**

- **ffmpeg** seeks over HTTP ranges to 0, 37, 95, and 171 s. Each seek decodes the **identical frame** (MD5) from the plaintext and the encrypted resource, in 101–123 ms either way.
- **A `<video>` element** in Chromium (the app's browser pane) loads each source, then seeks to 12 targets and waits until it can play. Medians are over two rounds:

  | Source | Metadata | Seek median | Seek max |
  |---|---|---|---|
  | Plain file (`register`) | 16 ms | 24–26 ms | 45 ms |
  | Plain stream (`register_stream`) | 17–19 ms | 27–30 ms | 45 ms |
  | Encrypted, 64 KiB chunks | 12–16 ms | 14–17 ms | 34 ms |

  Encrypted playback is indistinguishable from plain. The differences are noise. Decryption costs about a thousandth of a single core at this bitrate.

**Tamper resistance** (unit tests). Each of these is refused, and no plaintext from the bad chunk is returned:

- a flipped bit;
- two chunks swapped;
- a chunk spliced from another resource under the same content key;
- truncation to a chunk boundary, caught by the final-chunk flag;
- a wrong content key.

**Findings.**

1. **Use 64 KiB chunks.** They have the best seek latency at full throughput. Smaller chunks cost throughput; larger ones add per-seek latency for no gain.
2. **Align ciphertext chunks to 64 KiB:** plaintext chunks of 65,520 bytes plus a 16-byte tag. Torrent piece sizes are powers of two of at least 16 KiB, so every ciphertext chunk then sits inside one piece or covers whole pieces. A seek never waits for an extra piece because a chunk straddles a boundary. The numbers above are unchanged by this (a 0.02% difference in chunk size).
3. **The gateway needs no change.** `DecryptingReader` is a `MediaReader`. The product version stacks it on top of the torrent `FileStream` reader, which already waits for verified pieces, so integrity (torrent plus SHA-256) and authenticity (AEAD) compose.
4. The reader keeps exactly one decrypted chunk. The gateway's 256 KiB response reads cross at most five chunks, and memory per stream is about 64 KiB.

## 2. Sign-in: the issuer as relying party, with a loopback redirect

**Setup.** `src/bin/oauth.rs` runs three roles on separate loopback ports:

- a mock GitHub-style provider: `/authorize` consents automatically, plus `/token` with PKCE and `/user`;
- a mock issuer: `/auth/start`, `/auth/callback`, `/auth/redeem`;
- the app side: state plus PKCE, a one-shot `127.0.0.1:0` listener, and a redeem signed with an Ed25519 learner key.

The issuer runs its own PKCE flow with the provider, mints a 60-second one-time code, and redirects the browser to the app's loopback.

Modes:

- `headless`: a redirect-following HTTP client plays the browser;
- `print`: prints a start URL for a real browser to open;
- `system`: opens the default browser;
- `checks`: negative cases.

**Results.**

| Scenario | Result |
|---|---|
| Headless, two "machines" | Pass. Each sign-in takes about 7 ms locally. The second machine (a new learner key) gets the same subject (`github:4242`) and the same purchases; the device count is 2. |
| **Real browser** (Chromium in the browser pane; `print` mode) | Pass. The issuer and provider redirect chain lands on `http://127.0.0.1:<port>/callback`, which shows "Signed in — you can close this tab". The app redeems, and the second machine also passes. |
| Code replay | Refused. A code redeems once. |
| Wrong PKCE verifier | Refused, and the code is burned, so a guess cannot be retried. |
| Redeem signed by a key other than the one presented | Refused. |
| Redirects other than `http://127.0.0.1:<port>/callback` (`https://evil…`, `localhost`, no port, other path, extra query) | Refused at `/auth/start`. |
| Fourth machine | `409 device limit reached`. An already-known machine still signs in. |
| Callback with a forged `state` | Refused by the app. |

**Findings.**

1. **The issuer as relying party works.** The desktop app never holds a provider client secret or token. It only sees the issuer's one-time code, which is useless without its PKCE verifier and a learner key signature.
2. **Accept only the literal `127.0.0.1` with a port** (RFC 8252 §7.3), not `localhost`, which can resolve elsewhere. Return a plain "close this tab" page from the loopback.
3. **Burn a code on any failed redeem.** The spike removes the grant before checking it, so retrying against a stolen code fails closed.

**Untested; carried to slice 7.**

- **Real Google and GitHub.** These need OAuth app registrations from the maintainer: a GitHub OAuth App, and a Google OAuth client with the `openid` scope.
- **Windows and macOS.** The opener differs: `explorer`/`ShellExecute` on Windows, `open` on macOS. Firewall prompts for a loopback listener are not expected for `127.0.0.1`, but that is unverified.
- **`system` mode on Linux** was not run, to avoid opening a browser on the maintainer's desktop.
- **Launching the browser from the AppImage.** The AppImage's `LD_LIBRARY_PATH` and GStreamer variables can leak into `xdg-open` and break the browser it starts. The product should launch it through `tauri-plugin-opener`, or with the AppImage variables removed, and test the packaged build.

## 3. HPKE crate

| Crate | Version | License | MSRV | RustCrypto line | Verdict |
|---|---|---|---|---|---|
| **`hpke`** (rozbb) | 0.14.1 | MIT/Apache-2.0 | 1.85 | `aead` 0.6, `chacha20poly1305` 0.11, `getrandom` 0.4, `hkdf` 0.13: **the workspace's versions** | **Choose** |
| `hpke-ng` | 0.2.0 | MIT/Apache-2.0 | **1.96** (the workspace pins 1.93) | `aead` 0.5, `chacha20poly1305` 0.10, `aes-gcm` 0.10 | Reject: duplicates 10 RustCrypto crates, and its MSRV is above the workspace's |
| `hpke-rs` (libcrux) | 0.8.0 | **MPL-2.0** | — | — | Reject: MPL-2.0 is not on `deny.toml`'s allow list |

**Evidence.**

- **RFC 9180 known-answer tests.** `hpke` 0.14.1's own suite (`--features kat`, the RFC test vectors) passes: 148 tests.
- **Interop.**
  - `hpke` seals a 32-byte content key for X25519/HKDF-SHA256/ChaCha20-Poly1305, with `info = "zeron.license.v1"` and the course ID and version as associated data, and `hpke-ng` opens it. The reverse also works.
  - A different course in the associated data, or a different learner key, is refused.
  - A wrapped key is 32 B (encapsulated key) + 48 B (sealed content key).
- **New crates.** Added to the spike's dependency tree, `hpke` with `default-features = false, features = ["alloc", "getrandom", "x25519", "chacha"]` brings in only **two crates new to the workspace lock**: `hpke` and `x25519-dalek` 3.0.0. The latter uses the same `curve25519-dalek` 5 as `ed25519-dalek` 3 and is BSD-3-Clause, which is allowed.

## Decision

- **Encrypted packages (slice 2):** use `zeron.chunked-xchacha20poly1305.v1` with 64 KiB ciphertext chunks (65,520-byte plaintext chunks). Stack `DecryptingReader` on the verified torrent reader. The gateway is unchanged.
- **Licenses (slice 4):** wrap content keys with `hpke` 0.14.1 (X25519, HKDF-SHA256, ChaCha20-Poly1305, base mode), with `info = "zeron.license.v1"` and the course ID and version as associated data.
- **Sign-in (slice 7):** make the issuer the relying party. The app uses state, PKCE, a literal `127.0.0.1` loopback callback, and a redeem signed with the learner key. Codes are one-time, last 60 s, and are burned on failure. Real-provider, Windows/macOS, and AppImage browser-launch checks belong to that slice.
